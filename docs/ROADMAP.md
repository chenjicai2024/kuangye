# Kuangye 通用视觉智能体底座 · 长期规划

## 一、愿景与定位

**定位**：通用桌面视觉智能体底座 — 通过视觉理解桌面环境，像人类一样操作任意 GUI 应用。

**核心价值**：让 AI 能够"看懂屏幕、理解上下文、执行操作、从经验中学习"，适用于任何桌面应用场景，不限于特定软件。

**核心理念**：

1. **通用视觉能力**：VLM 识别界面元素、理解操作流程、规划下一步动作
2. **双捕获策略**：VLM 自动检测（智能感知）+ 框选器（人工指定），覆盖所有场景
3. **工作记忆通用**：trace 记录 + 经验卡片，跨应用、跨场景的通用学习底座
4. **大模型负责"看"和"想"**，模块化知识负责"怎么做"

## 二、程序架构详解

### 2.1 三层事件驱动架构

```
RuntimeHost（事件队列引擎）
  └─ GenericChannelSession（See·Think·Do·Learn 状态机）
       └─ DesktopDevice（感知 + 动作层）
            └─ VLM Route     — 视觉模型自动检测（智能感知）
            └─ Overlay Wizard — 人工框选（确定性控制）
```

**事件队列机制**：所有操作通过事件队列串行化，避免异步竞态。`RuntimeHost` 从队列头部取事件，交给状态机处理，状态机可以往队列尾部追加新事件。

### 2.2 双捕获策略

| 维度 | VLM 路线（智能感知） | Overlay Wizard 路线（人工指定） |
|------|---------------------|-------------------------------|
| 布局测量 | VLM 自动识别 UI 元素 | 用户自由绘制矩形 |
| 适用场景 | 有明确 UI 结构的应用 | 任何桌面应用 |
| 未读检测 | 红点扫描、状态变化检测 | 像素 diff 检测 |
| 会话切换 | 自动检测并切换 | 单会话模式 |
| 输入框定位 | VLM 反推坐标 | 用户绘制的矩形坐标 |

### 2.3 工作记忆模块（完全通用）

工作记忆是项目的通用底座，分为三个能力层次：

```
L1 记录 Trace      每次执行 = 结构化工作轨迹（本地、append-only、数据不出企业）
L2 回放/评测       轨迹时间轴回放 + 同场景跨模型/跨版本的量化对比
L3 继承 Memory     轨迹 + 人工接管 → 归纳「经验卡片」(SOP) → 注入运行时 → 效果可度量
```

**核心组件**：

- **TraceRecorder**：每步落 `trace.jsonl` + 截图，记录完整的操作轨迹
- **ExperienceStore**：经验卡片 `scenario/guidance/rationale`，不限场景
- **learn-from-session**：从轨迹中归纳可复用的操作经验
- **注入机制**：`RuntimeHost.runProviderWithMemory()` 自动注入卡片到 ProviderInput

### 2.4 Provider 插件系统

- **架构**：`manifest.json`（配置 schema）+ `provider.bundle.js`（运行时）
- **加载**：内置 Doubao（共享视觉密钥）或用户安装的第三方 provider
- **接口**：`createProvider(context)` → `{ run(input): AsyncIterable<ProviderEvent> }`

### 2.5 Skill HTTP Server

3 个端点（`POST /skill/start`、`POST /skill/pause`、`GET /skill/status`），监听 127.0.0.1:12680。外部 AI agent 通过 HTTP 控制引擎启停。

## 三、技术路线

### Phase 1：核心能力验证（已完成）

**目标**：验证"视觉智能体"核心理念，构建完整的 See → Think → Do → Learn 闭环

**已实现**：

- ✅ 通用视觉识别引擎（VLM + 框选器双捕获策略）
- ✅ 可视化动作链编辑器（拖拽式 RPA 流程设计）
- ✅ 工作记忆系统（trace + 经验卡片）
- ✅ Provider 插件机制（可扩展的模型服务接入）
- ✅ Skill HTTP API（外部 AI Agent 控制）

### Phase 2：通用化增强

**目标**：消除特定应用耦合，提升通用性和可扩展性

**做什么**：

1. **应用配置泛化**：将特定应用的 prompt、布局规则提取为可配置模块
2. **VLM prompt 模板化**：视觉识别 prompt 改为变量填充，支持不同 UI 布局
3. **状态机守卫放宽**：去除硬编码的应用类型判断
4. **窗口查找泛化**：支持任意窗口标题/进程名匹配

### Phase 3：垂直场景验证

**目标**：验证通用底座在特定垂直场景的深度能力

**候选场景**（选择 1-2 个验证）：

- 企业 IM 自动化（微信、钉钉、飞书等）
- 后台管理系统操作
- 表格/ERP 数据录入
- 桌面应用测试自动化

### Phase 4：生态与标准化

**目标**：构建开发者生态，推动行业标准

**做什么**：

- 发布开放的 work-trace 规范（兼容 OTel GenAI spans）
- 构建 Provider / Skill 市场
- 提供完整的 SDK 和开发文档
- 社区驱动的场景扩展

## 四、设计原则

1. **简单优先**：能用配置解决的不写代码
2. **渐进式扩展**：先在一个场景跑通，再扩展到其他场景
3. **不过度设计**：保持核心精简，通过插件机制扩展
4. **工作记忆不动**：trace + 经验卡片是通用底座，不绑定特定场景
5. **通用性优先**：任何新功能都必须考虑跨应用场景
